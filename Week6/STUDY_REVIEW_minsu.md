### 📍 Topic B - 인덱스 & 쿼리 성능

---

### 1️⃣ 핵심 개념 한 줄
인덱스(Index)는 **데이터 조회 성능을 향상시키기 위해 별도의 자료구조에 검색 키를 정렬하여 저장하는 구조**로, 테이블 전체를 스캔하지 않고 원하는 데이터를 빠르게 찾을 수 있도록 도와줍니다.

---

### 2️⃣ 동작 원리 요약
대부분의 관계형 데이터베이스는 **B-Tree 구조의 인덱스**를 사용한다.

데이터 조회 과정은 다음과 같다.

1. 인덱스에 검색 키 값이 정렬된 상태로 저장되어 있음
2. 쿼리 실행 시 DB는 먼저 **인덱스를 탐색**
3. 인덱스에서 조건에 맞는 **레코드의 위치(포인터)** 를 찾음
4. 해당 위치를 통해 **실제 테이블 데이터에 접근**

### 4️⃣ 주의 포인트
- **인덱스는 조회 성능을 높이지만 쓰기 성능은 떨어질 수 있음**
    - INSERT / UPDATE / DELETE 시 인덱스도 함께 갱신해야 하기 때문

- **인덱스를 많이 만들수록 성능이 좋아지는 것은 아님**
    - 인덱스 관리 비용 증가
    - 디스크 공간 증가

- **카디널리티가 낮은 컬럼은 인덱스 효과가 떨어질 수 있음**
    - 예: gender, status 같은 컬럼

- **LIKE '%keyword' 형태는 인덱스를 타지 못할 수 있음**

- **복합 인덱스는 왼쪽부터 사용됨 (Leftmost Prefix Rule)**
- **복합 인덱스는 왼쪽부터 사용됨 (Leftmost Prefix Rule)**

### 5️⃣ 자주 나오는 면접 질문 (선택)
**Q1. 인덱스를 사용하는 이유는 무엇인가요?**

A.  
데이터를 정렬된 구조로 저장하여 **검색 속도를 빠르게 하기 위해 사용합니다.**  
인덱스를 사용하면 테이블 전체를 스캔하지 않고 필요한 데이터의 위치를 빠르게 찾을 수 있습니다.

---

**Q2. 인덱스의 단점은 무엇인가요?**

A.  
조회 성능은 향상되지만 **데이터 변경 시 인덱스도 함께 수정되어야 하기 때문에 쓰기 성능이 저하될 수 있습니다.**  
또한 인덱스를 유지하기 위한 **추가 저장 공간이 필요합니다.**

---

**Q3. 복합 인덱스는 어떤 규칙으로 동작하나요?**

A.  
복합 인덱스는 **Leftmost Prefix Rule**을 따릅니다.  
즉, 인덱스의 **왼쪽 컬럼부터 순서대로 조건이 사용될 때만 인덱스를 활용할 수 있습니다.**

---

**Q4. 인덱스를 사용해도 쿼리가 느릴 수 있는 이유는 무엇인가요?**

A.

- 인덱스 선택도가 낮은 경우
- LIKE '%keyword' 패턴 사용
- 함수 사용 (예: `WHERE YEAR(created_at) = 2024`)
- 잘못된 인덱스 설계
- 많은 범위를 조회하는 경우

이런 경우 DB는 **Full Table Scan을 선택할 수도 있습니다.**
