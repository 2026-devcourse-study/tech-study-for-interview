### 📍 Topic B – 레이어드 아키텍처 & 책임 분리

---

### 1️⃣ 핵심 개념 한 줄
> Layered Architecture : 시스템을 유사한 관심사끼리 계층화하여 각 계층이 자신의 역할에만 집중하게 함으로써 유지보수성과 확장성을 높이는 방법론이다. 애플리케이션을 역할별로 계층을 나누어 책임을 분리하는 구조다. <br></br>
> Controller는 요청을 받아 DTO로 변환하고 응답을 반환하는 역할 <br></br>
> Service는 비즈니스 로직과 트랜잭션을 담당 <br></br>
> Repository는 데이터 접근을 담당하며 DB와의 상호작용을 추상화 <br></br>
> 각 계층은 단일 책임 원칙에 따라 분리되어야 함 <br></br>

---

### 2️⃣ 동작 원리 요약

- **왜 필요한가?**
  - 복잡한 시스템에서 변경에 강하고, 테스트에 용이하고, 유지보수하기 쉽게 만들기 위해 필요하다.
- **어떻게 동작하는가?**
  - Layered Architecture는 사실상 상위 계층이 하위 계층을 사용하고, 하위 계층은 상위 계층을 모르게 하는 구조이다. (단방향 의존 구조)

### 5️⃣ 자주 나오는 면접 질문 (선택)

- Q. Layered Architecture가 뭔가요?
    - A : 
    ```
    Layered Architecture(계층형 아키텍처)는 애플리케이션을 역할별로 계층을 나누어 책임을 분리하는 구조다.
    시스템을 유사한 관심사끼리 계층화하여 각 계층이 자신의 역할에만 집중하게 함으로써 유지보수성과 확장성을 높이는 방법론이다.
    ```

- Q. Controller / Service / Repository 역할을 설명해주세요.
    - A : 
    ```
    Controller는 요청을 받아 DTO로 변환하고 응답을 반환하는 역할을 합니다.
    Service는 비즈니스 로직과 트랜잭션을 담당합니다.
    Repository는 데이터 접근을 담당하며 DB와의 상호작용을 추상화합니다.
    각 계층은 단일 책임 원칙에 따라 분리되어야 합니다.
    ```
    
- Q. Service가 비대해지면 어떤 문제가 생기나요?
    - A : 
    ```
    Service가 비대해지면 하나의 클래스가 여러 책임을 가지게 되어 단일 책임 원칙(SRP)이 깨지고,
    테스트가 어려워지며 변경에 취약해집니다. 결국 유지보수 비용이 증가합니다.
    ```
    
- Q.도메인 로직은 어디에 두는 게 좋은가요?
    - A : 
    ```
    핵심 비즈니스 규칙은 도메인 객체(Entity)에 두는 것이 좋습니다. 이를 통해 객체가 자신의 상태와 행위를 함께 가지게 되고,
    응집도가 높아지며 객체지향적인 설계가 됩니다.
    ```
    
- Q. DTO와 Entity를 왜 분리해야 하나요?
    - A : 
    ```
    Entity는 비즈니스 모델이며, DTO는 계층 간 데이터 전달을 위한 객체입니다.
    두 개념을 분리하면 계층 간 의존성을 줄이고, API 스펙 변경이 도메인에 영향을 주지 않게 됩니다.    
    ```

### 6️⃣ 꼬리 질문 & 대응 포인트 (선택)

- 꼬리 질문: Service가 비대해지면 어떻게 해결하냐요?

    ```
    도메인 객체에 행위를 위임하거나, 도메인 서비스로 분리하고, 애플리케이션 서비스는 조정자 역할만 하도록 설계합니다.
    
    ```


- 꼬리 질문: Service는 트랜잭션만 담당하면 되나요?
- 대응 논리:
    ```
    이상적으로는 애플리케이션 흐름 제어와 트랜잭션 경계를 담당하고,
    실제 비즈니스 규칙은 도메인에 위임하는 것이 좋습니다.
    ```


- 꼬리 질문: 모든 로직을 도메인에 넣어야 하나요?
- 대응 논리:
    ```
    아닙니다. 여러 도메인을 조합하는 로직은 애플리케이션 서비스에 두는 것이 적절합니다.
    ```
