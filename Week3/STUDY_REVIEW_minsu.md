### 📍 주제 B: 성능 / 읽기·쓰기 (민수)

---

### 1️⃣ 핵심 개념 한 줄
> 대부분의 서비스는 쓰기보다 읽기 트래픽이 훨씬 많기 때문에, 읽기 성능을 중심으로 조회 구조와 연관관계 로딩 전략을 설계해야 합니다.

---

### 2️⃣ 동작 원리 요약

#### 왜 중요한가?

- **읽기 요청은 트래픽의 대부분을 차지**
  - 대부분의 서비스는 읽기 트래픽이 쓰기보다 훨씬 많음 (예: SNS, 커머스)
  - 잘못된 조회 설계는 불필요한 쿼리 폭증(N+1), DB 부하 증가, 응답 지연으로 이어짐
  - 👉 성능 문제는 기능보다 늦게 발견되고, 비용은 더 큼

#### 읽기 작업 vs 쓰기 작업 특성

| 구분 | 읽기(Read) | 쓰기(Write) |
|------|-----------|------------|
| **빈도** | 높음 | 낮음 |
| **우선순위** | 응답 속도 | 정합성 |
| **핵심 전략** | 캐시, 인덱스, 조회 최적화 | 트랜잭션, 락, 무결성 |
| **특징** | 정합성보다 속도 우선하는 경우 많음 | 일관성과 안정성 중심 |

👉 읽기/쓰기 특성에 따라 설계 포인트가 다름

#### 읽기 많은 서비스 설계 전략

- **조회 전용 API / DTO 분리**: 필요한 데이터만 조회 (엔티티 그대로 반환 ❌)
- **인덱스 적극 활용**: 자주 조회되는 컬럼에 인덱스 추가
- **캐싱 레이어 도입**: Redis 등으로 반복 조회 데이터 캐싱
- **Read Replica 구성**: 읽기 전용 복제 DB로 트래픽 분산
- **CQRS 패턴 고려**: 쓰기 모델과 읽기 모델을 분리

#### N+1 문제

**발생 원인**
- 연관관계가 LAZY 로딩일 때
- 컬렉션/연관 엔티티를 반복 접근
- 징후: 조회 1번 했는데 쿼리가 수십 번 실행, 로컬에선 티 안 나고 트래픽에서 터짐

**해결 방법**
1. **Fetch Join**
   - 연관 엔티티를 한 번에 조회
   - 장점: 직관적, 성능 확실
   - 단점: 페이징과 함께 쓰면 위험 (메모리 로딩)

2. **EntityGraph**
   - 선언적으로 연관관계 로딩 제어
   - fetch join보다 유연
   - 기본적으로 LEFT OUTER JOIN 사용

#### 페이징 주의사항

- **fetch join + 페이징 ❌**: 데이터 뻥튀기 → 메모리에서 처리
- **해결 방법**
  - ID 페이징 후 재조회
  - 조회 전용 쿼리 분리
  - Batch Size 설정 활용
- 👉 페이징은 항상 데이터 증가를 의식해야 함

### 3️⃣ 핵심 키워드

- `Read Heavy Service` - 읽기 트래픽이 압도적으로 많은 서비스
- `N+1 Problem` - 연관 엔티티 조회 시 추가 쿼리가 N번 발생하는 성능 이슈
- `Fetch Join` - JPQL에서 연관 엔티티를 한 번의 쿼리로 함께 조회
- `EntityGraph` - 어노테이션 기반으로 fetch 전략을 동적으로 지정
- `Lazy Loading` - 연관 엔티티를 실제 사용 시점에 조회하는 전략
- `CQRS` - Command Query Responsibility Segregation, 읽기/쓰기 모델 분리
- `Read Replica` - 읽기 전용 복제 DB로 읽기 트래픽 분산
- `Paging & Join` - 페이징과 조인 함께 사용 시 주의점

---

### 4️⃣ 주의 포인트

- ❗ **fetch join과 페이징 함께 사용 시**: 컬렉션 fetch join은 페이징이 메모리에서 처리될 수 있음 (데이터 뻥튀기, 성능 저하)
- ⚠️ **EntityGraph vs fetch join**: EntityGraph는 LEFT OUTER JOIN, fetch join은 INNER/LEFT 선택 가능
- ❗ **N+1 발견 방법**: 로그에서 `hibernate.show_sql=true` 설정으로 실행 쿼리 확인. 로컬에서는 잘 안 보이고 트래픽에서 터짐
- ⚠️ **읽기 복제본 지연**: Read Replica는 비동기 복제로 약간의 지연(Replication Lag) 존재
- ❗ **인덱스 과다 추가**: 읽기 성능을 위한 인덱스 과다는 쓰기 성능 저하 유발
- ⚠️ **무조건적 최적화 지양**: 트래픽 규모와 사용 빈도에 따라 최적화 여부 결정

### 5️⃣ 자주 나오는 면접 질문

#### Q1. **N+1 문제를 어떻게 발견하고 해결했나요?**

💬 **모범 답변**
```
로컬에서는 잘 안 보였지만, SQL 로그를 확인했을 때
조회 한 번에 다수의 쿼리가 반복 실행되는 걸 보고 N+1을 의심했습니다.

hibernate.show_sql=true 설정으로 쿼리를 확인한 결과,
Lazy Loading으로 인해 연관 엔티티마다 개별 쿼리가 발생하고 있었습니다.

이후 fetch join과 EntityGraph를 적용해 쿼리를 단건으로 줄였고,
페이징이 필요한 경우에는 조회 쿼리를 분리하거나 Batch Size를 설정해 해결했습니다.
```

**답변 포인트**
- Hibernate 쿼리 로그 확인 → Lazy Loading으로 발생한 추가 쿼리 확인
- fetch join 또는 EntityGraph 적용 → 쿼리 수 감소 확인
- 페이징 상황에서의 대안 제시

---

#### Q2. **쓰기보다 읽기 트래픽이 많은 서비스면 DB 설계는?**

💬 **모범 답변**
```
쓰기보다 읽기가 많기 때문에 조회 전용 API와 DTO를 분리하고,
인덱스와 조회 최적화에 집중했습니다.

Read Replica를 구성해 읽기 트래픽을 분산시키고,
자주 조회되는 데이터는 Redis 같은 캐싱 레이어를 추가했습니다.

경우에 따라 읽기 모델을 분리하는 CQRS 관점도 고려했습니다.
```

**답변 포인트**
- 조회 전용 API/DTO 분리
- Read Replica 구성, 캐싱 레이어(Redis) 추가
- CQRS 패턴 고려, 인덱스 최적화

---

#### Q3. **성능 튜닝 경험이 있나요?**

💬 **모범 답변**
```
커머스 상품 목록 조회 API에서 응답 시간이 3초 이상 소요되는 문제가 있었습니다.

쿼리 로그를 확인한 결과, N+1 문제로 상품 100개당
카테고리와 이미지를 개별 조회해 총 300개 이상의 쿼리가 발생했습니다.

fetch join으로 상품-카테고리-이미지를 한 번에 조회하도록 개선했고,
필요한 필드만 DTO로 변환해 메모리 사용량도 줄였습니다.

결과적으로 쿼리 수를 1~3개로 감소시켜 응답 시간을 300ms 이하로 개선했습니다.
```

**답변 포인트**
- 구체적인 문제 상황과 수치 제시
- 문제 발견 방법과 원인 분석
- 해결 방법과 개선 결과 (Before/After 수치)

### 6️⃣ 꼬리 질문 & 대응 포인트

#### 꼬리 질문 1: "fetch join과 EntityGraph의 차이는?"
**대응 논리**
- fetch join은 JPQL에 직접 명시하고 INNER/LEFT JOIN 선택 가능
- EntityGraph는 어노테이션으로 동적 설정하며 기본적으로 LEFT OUTER JOIN 사용
- 상황에 따라 선택: 명시적 제어가 필요하면 fetch join, 선언적 관리가 필요하면 EntityGraph

#### 꼬리 질문 2: "Read Replica 사용 시 주의점은?"
**대응 논리**
- 복제 지연(Replication Lag)으로 최신 데이터가 아닐 수 있음
- 쓰기 직후 읽기가 필요한 경우 Master DB를 사용해야 함
- 정합성이 중요한 도메인(결제, 금융)에서는 신중하게 적용

#### 꼬리 질문 3: "페이징과 fetch join을 함께 쓰면 왜 위험한가?"
**대응 논리**
- 컬렉션 fetch join 시 데이터가 뻥튀기되어 메모리에 모두 로딩
- JPA가 경고 로그를 출력하고 메모리에서 페이징 처리
- 대안: Batch Size 설정, 조회 쿼리 분리, ID 페이징 후 재조회
