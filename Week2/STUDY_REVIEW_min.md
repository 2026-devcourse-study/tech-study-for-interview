### 1️⃣ 핵심 개념 한 줄
> 동시성 문제 : 동일한 데이터에 대해 여러 사용자가 동시에 접근하여 수정하려고 할 때, 데이터의 일관성이 깨지는 현상 <br>
> 락(Lock) 매커니즘은 위와 같은 동시성 문제를 해결하기 위한 대표적인 방법 중 하나로 특정 자원을 한 번에 하나의 스레드만 사용할 수 있도록 "잠금"을 거는 장치이다. </br>
> 충돌이 적으면 낙관적 락, 충돌이 잦거나 정합성이 매우 중요하다면 비관적 락, 분산 서버 환경이라면 분산 락을 고려

### 2️⃣ 동작 원리 요약

- **왜 필요한가?**
  - 데이터의 원자성(Atomicity)을 보장하기 위함이다. 수정 중에는 다른 스레드가 접근하지 못하게 막아 데이터 정합성이 깨지는 것을 막는다.
  <br></br>
- **어떻게 동작하는가?**
  - 낙관락 : 동시 수정이 발생하지 않을 것이라고 낙관적으로 가정하는 방식
    - DB의 락 기능을 쓰는 게 아니라, 애플리케이션 레벨에서 버전(Version) 관리를 통해 해결
    - 동작 : 엔티티에 @Version 컬럼을 추가하여 관리
    - 데이터를 읽을 때 version 번호도 함께 읽음
    - 수정 시점에 내가 읽었던 버전이 맞는지 확인: `WHERE id = ? AND version = ?`
    - 그 사이 다른 사람이 수정해서 버전이 올라갔다면 OptimisticLockException이 발생하며 롤백됨 (버전이 다르다면 누군가 먼저 수정한 것)
    - 장점: 실제 DB에 락을 걸지 않아 성능상 이점이 있다.
    - 단점: 충돌이 났을 때 재시도(Retry) 로직을 개발자가 직접 구현해야 한다.
  
  - 비관락 : 동시 수정이 반드시 발생할 것이라고 비관적으로 가정하는 방식
    - DB가 제공하는 락 기능을 직접 사용
    - 동작 : 데이터를 읽는 시점부터 DB 테이블의 해당 행(Row)을 즉시 락을 걸어버림
    - 다른 트랜잭션은 락이 풀릴 때까지 대기해야 한다
    - 장점: 데이터 정합성을 강력하게 보장하며, 충돌 발생 시 재시도 로직이 필요 없음 (대기했다가 순서대로 처리되므로)
    - 단점: 성능 저하의 위험이 있고, 서로가 락이 풀리길 기다리는 데드락(Deadlock) 상태에 빠질 수 있다.
    - 동작 원리: 데이터를 수정하려는 스레드가 '락'을 획득해야만 작업을 수행할 수 있고, 작업이 끝나면 락을 반납하여 다음 대기자가 작업을 이어가게
  
  - 비관락 : 동시 수정이 반드시 발생할 것이라고 비관적으로 가정하는 방식

### 4️⃣ 주의 포인트

- ❗ 어떤 상황에서 무엇을 선택할까?
    - 충돌이 적고 성능이 중요하다면? -> 낙관적 락 (게시글 수정, 사용자 프로필 변경 등)
    - 충돌이 잦고 정합성이 매우 중요하다면? -> 비관적 락 (재고 관리, 선착순 쿠폰 발급 등)
    - 서버가 여러 대인 분산 환경에서 고성능을 원한다면? -> 분산 락 (DB에 가해지는 부하를 줄이고 싶을 때 사용)
    - 단순한 숫자 증가고 단일 서버라면? -> Synchronized

### 6️⃣ 꼬리 질문 & 대응 포인트 (선택)

- 꼬리 질문: 트랜잭션 격리 수준과 락의 차이는?
- 대응 논리:
```
격리 수준: 트랜잭션이 다른 트랜잭션의 변경을 얼마나 볼 수 있는지 제어 (DB 레벨)
락: 특정 데이터에 대한 동시 접근을 제어하는 메커니즘 (애플리케이션/DB 레벨)

격리 수준은 전역 설정이고, 락은 특정 엔티티나 테이블 단위로 적용된다.
```
<br>

- 꼬리 질문: 비관적 락의 종류인 PESSIMISTIC_READ와 PESSIMISTIC_WRITE의 차이점은 무엇인가요?
- 대응 논리:
```
PESSIMISTIC_WRITE: 배타적 락 (X-Lock)

다른 트랜잭션의 읽기/쓰기 모두 차단


PESSIMISTIC_READ: 공유 락 (S-Lock)

다른 트랜잭션의 쓰기만 차단, 읽기는 허용
```
</br>

- 꼬리 질문: 데드락은 언제 발생하고 어떻게 방지하나요?
- 대응 논리:
```
발생 상황:

트랜잭션 A: Product → Order 락
트랜잭션 B: Order → Product 락
서로 상대방이 보유한 락을 기다리며 무한 대기

방지 방법:

락 획득 순서 통일 (항상 같은 순서로 락 획득)
타임아웃 설정 (일정 시간 후 락 획득 실패)
락 범위 최소화
트랜잭션 시간 단축
```
